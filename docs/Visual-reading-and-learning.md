# Visual reading and local correction learning

## 0.6.2 generation and field-assignment regression

The 0.6.1 field-value change was insufficient: a user confirmed version 0.6.1 (10) still assigned a company suffix to name and omitted email/address despite readable OCR. Controlled Windows model tests then exposed a generation-path difference: with identical photographs, OCR and the final instruction, constrained JSON generation omitted channels and produced bogus contacts; unconstrained generation returned both people and their complete separate details in one pass. Production no longer enables response-format constraints. The bounded JSON parser, type checks, channel validation and source review still apply to the generated response, including fenced JSON.

Complete readable OCR now precedes optional spatial metadata instead of disappearing when represented in source rows. Source rows keep original order. The shorter extraction instruction and fresh-context repair avoid accumulating the failed generation inside the 4096-token context. Learned hints are not truncated mid-JSON. Corporate-suffix-only names request repair; complete model-written company/address values can cover their separate OCR lines; a more complete grounded repair can be accepted when issue counts tie without discarding people/channels.

Final unconstrained synthetic model checks passed two people with separate channels, a forced company-suffix failure repair (one correct complete person), and image recovery when OCR omitted name/title/address. Exact real-model responses are versioned under `app/src/test/resources/recognition/` and run through the production parser and form reconciliation in JVM tests. These are Windows CPU model tests with synthetic OCR positions, not Android device or real-camera acceptance. The user's private failing card was not obtained, so its exact failure has not been reproduced.


## 0.6.1 field-population regression fix

OCR and visual interpretation still share one extraction request: both card photographs, OCR text, positioned source regions and alternative readings are supplied together. The visual model assigns readable text to fields and people. It now returns explicit field values; source IDs are optional review annotations instead of the primary representation of names, roles, companies and addresses. The previous ID-only contract could leave those fields blank when its references were missing or disputed.

An entirely empty contact proposal requests one contextual repair, then fails validation if still empty. A failed reread preserves the existing draft. A successful but sparse reread preserves unresolved earlier values only for the matched person and marks them for review; explicit user-cleared fields stay empty. Explicit new channel readings replace old ones rather than merging an earlier mistake back in. Visual email proposals are not silently replaced by a differing OCR email, and visually read address endings are no longer trimmed merely because OCR omitted them. Uncorroborated values remain reviewable with warnings. No account name or external inference provider is involved.

Actual Windows CPU model checks passed a synthetic card with three phones/two emails/two websites/full address, and recovered name/title/address from its photograph when those values were removed from supplied OCR. A two-person case remains imperfect: a contextual repair recovered the omitted person but corrupted their email. This is a recorded model limitation, not a passing accuracy gate. These checks use synthetic OCR text/positions, not Android OCR.

Regression coverage includes explicit values with bad/missing OCR references, disagreement metadata, three distinct labelled phone numbers, multiple emails/websites, full addresses, first-draft storage roundtrip, sparse rereads, protected clears and reordered people. Synthetic/host checks do not establish accuracy on every real photographed card or Galaxy S26 performance.

## Implemented

- LiteRT-LM Android 0.17.1 runs the Gemma 4 E2B vision-language model on device. Front/back preview photographs and bounded OCR text are inputs; the account profile is not an input. There is no remote inference fallback.
- Visual reading requires a 64-bit Android native runtime. Download/extraction checks both the current process and device 64-bit ABI support, and native-library linkage failures are mapped to a readable failure so OCR/manual review remains available. This is not a guarantee that every 64-bit phone has sufficient memory or compatible acceleration.
- The decoder runs on CPU. Vision initially uses GPU; a reported LiteRT-LM JNI failure triggers one local CPU-vision retry with a fresh engine/conversation and a separate cache directory. Only a successfully parsed CPU result records the preference to use CPU vision on later scans. That preference is tied to the runtime version, pinned model hash and device build fingerprint. CPU vision is an implemented upstream backend, but our exact model/device combination still needs successful execution; no remote service is substituted.
- Runtime allocation is bounded to a 4,096-token context, 1,200 output tokens and 280 visual tokens per image. A single-sided scan allocates one image slot; a two-sided scan allocates two. OCR input is capped at 2,000 characters total (1,000 per side when both are present), and local hints at 600 characters. Original stored OCR is preserved. A process-wide mutex serializes extraction and the SDK's global visual-budget flag. Lower visual resolution may affect small-print recognition; the bounded configuration passed the three fictional Android fixtures recorded below, while real-photograph accuracy remains unmeasured.
- Before engine initialization, Android low-memory status or less than 2 GiB available memory produces a typed, user-safe message suggesting closing other apps or reviewing text suggestions. The ViewModel surfaces that message without exposing raw native errors. This heuristic is not a minimum-device-RAM specification or a guarantee against process termination. Native linkage failures are also mapped safely, including configuration of the experimental flag.
- The public model download is pinned to revision `b3ca0d2f076785a8f4b2219ddbd2bdb99954eae1`, size 2,588,147,712 bytes, SHA-256 `181938105e0eefd105961417e8da75903eacda102c4fce9ce90f50b97139a63c`. It is downloaded separately, can resume, and becomes usable only after checksum verification. Downloading does not send contact information to the model host.
- The model can return multiple contacts. Review/save each separately; a common `sourceScanId` records provenance. Each contact owns independent image copies so deleting one person cannot delete another person's images. This uses more storage than image deduplication, deliberately preserving existing ownership/deletion guarantees.
- The review queue and original proposals survive ordinary activity/process recreation through SavedStateHandle. Images are retained until the queue finishes or is discarded. A user can skip a proposed person.
- Two-sided previews turn through 180 degrees, switch face at the midpoint, and counter-rotate the visible face. The system animator setting disables the turn animation. Device frame pacing is not measured yet.
- OCR grounding checks whole tokens rather than substrings: a short name or email cannot be confirmed merely by appearing inside another value. Semicolon-separated phone values are checked separately. Source presence does not prove which person owns a value.
- Malformed model output is rejected. Unconfirmed OCR values are explicitly flagged; raw OCR is never augmented with model output. Visual reading failure leaves a manual review draft and identifies basic text suggestions as such.
- The earlier text-only BERT NER prototype is no longer called by scanning, and its assets are excluded from application packaging. The existing MiniLM semantic-search model has a separate purpose and remains bundled.

## Actual model evaluation

`scripts/Create-VisionFixtures.py` creates six fictional card documents. `scripts/Evaluate-VisualModel.py` runs actual local image inference and compares expected fields. Results: `tests/vision/results-gpu.json`.

All six passed this small evaluation: single person, two people in columns, two people in rows, front/back, business-only without a person's name, and printed misleading instructions. Two-person tests check each person's own phone and email. The initial single-case cold run took 7.27 seconds to initialize and 39.20 seconds to infer. In the subsequent six-case run, initialization took 0.96 seconds and inference ranged from 10.78 to 27.64 seconds. These are Windows development-computer timings, not Android performance figures. The image evaluation does not yet include OCR context or correction hints.

These clean synthetic images do not establish accuracy on real photography, unusual names, multilingual cards, glare, angled cards, or all layouts. No physical Android phone was connected during the initial evaluation. Do not claim production accuracy or phone latency from these tests.

The initial opt-in Android GPU run using x86_64/SwiftShader failed after 22.35 seconds while creating the conversation: the vision encoder could not compile (`compiled_model.cc`, line 286). The subsequent CPU-fallback run with the original 8,192-token context on a 4 GB Android emulator was terminated by Android's low-memory killer after approximately 126 seconds. The final recorded resident footprint was 2,364,664 kB with 1,028,884 kB swapped. This was process termination, not a managed Java exception, and produced no completed field-accuracy result.

The replacement configuration above (4,096 context / 280 visual tokens per image / memory preflight) passed actual OCR and Gemma inference on an API 35 x86_64 Android emulator with 4 GB RAM. The single-person fixture completed in 76,538 ms including OCR; the two-column fixture completed in 47,485 ms, preserving each person's own phone and email. Native CPU inference was 66,103 ms for the first fixture after GPU compilation failed and 46,405 ms for the subsequent fixture using the remembered CPU preference. Evidence: `.tools/cpu-fallback-device.log`.

The final combined Android run passed all 14 tests in 150.225 seconds: 13 UI/component regressions plus one opt-in real-model test containing three fixtures. On the 4 GB API 35 x86_64 emulator, including OCR, single-person extraction took 61,669 ms, two-column/two-person extraction took 29,506 ms, and front/back extraction took 26,759 ms. The front/back case exercised two-image allocation, combined fields and unchanged per-side OCR; the multi-person case verified each person's phone/email ownership. Evidence: `.tools/final-v031-device.log`.

All 36 cloud JVM tests and lint passed in the final release build; the 8 auth-handler and 14 Firestore rules tests passed, and the updated rules are deployed. Company-only record save/display support is implemented. Emulator GPU failure does not establish physical Android GPU incompatibility, and these emulator timings are not physical-phone performance figures.

Native initialization is synchronous and may not respond promptly to coroutine cancellation. Streaming inference explicitly calls `cancelProcess()` during cleanup because the upstream Flow wrapper does not automatically cancel native work. Cancelled conversations are discarded rather than reused. A Kotlin exception handler cannot recover a native process crash; physical-device measurements and broader real-photograph testing remain necessary before general performance/accuracy claims.

## Automatic personal learning: implemented companion weight training

Saving a corrected scanned proposal automatically provides eligible training labels. Only changed fields whose corrected value appears in the original OCR are eligible; unchanged AI output, personal notes, externally added information and values assigned ambiguously to multiple corrected fields are excluded. Clearing or changing an earlier learned field also removes that card's superseded training evidence. There is no training button or required labelling workflow.

The companion classifier is a seven-class linear softmax model for name, role, company, phone, email, website and address. It trains actual weights with bounded stochastic gradient descent. Its features combine the existing bundled MiniLM's 384-dimensional sentence embeddings with OCR line position, line size, side, character shape and character patterns. This can generalize beyond an exact corrected phrase. OCR coordinates refer to the upright image, are normalized, and are preserved across ordinary process recreation. Ambiguous repeated lines contribute text features without guessed coordinates.

**Gemma's weights remain frozen.** The companion proposes high-confidence field labels for text on the current card; those fallible hints accompany the current images during visual inference. It neither generates missing contact values nor establishes person-to-phone ownership. Current image interpretation still handles multiple people and front/back associations. Exact correction memory remains a complementary mechanism, with conflicting phrase labels withheld. The companion cannot reintroduce those conflicting phrases or override an explicit remembered correction.

Training is automatically queued through WorkManager and waits for charging, device idle and sufficient battery. Android determines when these constraints permit execution; saving an edit does not imply an immediate model update. No foreground training notification, manual training approval or cloud training service is used. Training data is capped at 280 examples; exact phrase memory is capped at 100 labels.

At least six distinct evidence groups are needed before a candidate can be evaluated. Normalized front/back OCR is fingerprinted to group people from a shared scan and avoid counting identical re-imports as independent evidence, with source scan ID/card ID as fallback. Repeated photographs with different OCR can still form separate groups. Entire groups are held out from candidate training. A candidate replaces the active weights only when held-out cross-entropy improves, total accuracy does not decline, and accuracy for every represented field does not decline. Rejected candidates leave existing weights untouched. These small personal validation sets do not guarantee improvement on unseen cards or a monotonic end-to-end accuracy increase.

Examples, semantic vectors, field labels and weights are encrypted using account-scoped Android Keystore AES-GCM keys. The trainable store lives in `noBackupFilesDir`; none of this learning data enters Firebase or R2. The classifier retains derived OCR evidence and features, not an extra training copy of each photograph. Existing card-image cloud storage is separate from this local learning system.

Disabling learning cancels queued work. Sign-out cancels that account's training; sign-in reschedules retained work. Workers check the active account before and throughout training. Reset and account deletion remove the learning files and keys. Deleting a card removes its examples and invalidates learned weights, which are subsequently retrained from retained evidence. A generation/revision check prevents concurrent reset, deletion or correction from being overwritten by stale training. Native embedding inference and SGD run outside storage locks so disabling/resetting need not wait for a training loop.

## Companion verification status

`VisualModelDeviceTest` is a separate opt-in Android integration test. Pass instrumentation argument `visualModelTest=true` after preinstalling the verified model at the app's `filesDir/visual-model/gemma-4-e2b.litertlm`. It runs real OCR and `VisualModel.extract` on the fictional single-person, two-column and front/back fixtures, verifies field ownership and grounding, and reports hardware/timing metadata without model responses or private content. Without the argument it is explicitly skipped, not evidence of a model-inference pass. Opting in without an installed model fails the test. Optional argument `visualModelFixture=two_sides` runs only the front/back case; without a fixture selector all three cases run.

Added JVM tests cover weight changes, inference on unseen text with related semantic features, scan-group holdout separation, inadequate evidence, rejected regressions, cancellation and non-finite layout rejection. Added Android tests exercise the actual bundled MiniLM plus classifier, encrypted feature storage and reset during in-flight training. Test files alone are not evidence of passing execution; current executed results belong in `docs/Verification.md`.

The six fictional desktop Gemma fixtures above passed before this integration. They do not establish the accuracy of the combined OCR, personalized hints and vision pipeline. Physical Android performance, learning gains over real user corrections, multilingual performance, generalization across unfamiliar typography, energy use and long-term drift still require measurement. The companion currently learns field classification, not new vision-model representations or arbitrary visual reasoning.
